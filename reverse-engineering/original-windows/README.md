# Декомпиляция оригинального Windows EXE

Здесь находится фактический результат локальной декомпиляции
`PostgreSQL_JOIN90.exe` из предоставленного Windows-архива через Ghidra 12.2.
Выгружены все 66 скомпилированных функций приложения `main.*`, включая
обработчики локального сервера, SQL-проверки, сохранение и экспорт работ.
В таблице метаданных проиндексированы все 7 770 записей Go, включая
стандартные библиотеки и служебную запись `go:buildid`.
Реализации стандартной библиотеки отдельно не декомпилировались.

- [pseudocode/platform_windows.c](pseudocode/platform_windows.c): Windows API.

- [Карта API оригинала](../../docs/ORIGINAL-API.md): HTTP-маршруты,
  проверки доступа и побочные эффекты.
- [assembly/](assembly/): машинные инструкции с адресами и исходными байтами.
- [decompilation-results.tsv](decompilation-results.tsv): статус каждой функции.

В начале каждой функции указаны её оригинальное имя, адрес в EXE, путь и номер
строки из метаданных Go. При сверке 12 175 инструкций совпали все 63 930 байт
машинного кода в выгрузке. [Результат сверки](VERIFICATION.json)

## Ограничения

За пределами восстановления остались исходные `.go`-файлы с комментариями,
оригинальными именами локальных переменных и точными объявлениями типов,
а также полный проект для повторной сборки Windows EXE. Выгрузка `.c` содержит
C-подобный псевдокод для изучения машинного кода. Сверка байтов с EXE
подтверждает точность дизассемблирования в проверенных диапазонах.
Сигнатуры и типы в псевдокоде требуют сверки с ассемблером и поведением EXE.

Автоматический разбор информации о типах (RTTI) Go 1.27.4 остановился
на сообщениях Ghidra `Untested Go version [1.27.4]` и
`unable to get GoRttiMapper`. Имена и границы функций восстановили через
`debug/gosym`. Для уточнения Go-структур, сигнатур и строк используют машинный
код и данные EXE. [Манифест декомпиляции](manifest.json)

## Что сохранилось из оригинала

Оба JSON с материалами, четыре файла веб-интерфейса, `engine.mjs` и
`training_database.sql` побайтно совпадают с оригинальными ресурсами.
В EXE курс хранится во встроенной файловой системе Go. Загрузчик читает
`content/pg_join.json` и `content/pg_fixtures.json` через `embed.FS.ReadFile`
и разбирает их как JSON. Порт читает те же файлы с диска при запуске.
Обе версии вернули одинаковый каталог из 12 заданий и 7 разделов теории.
В обеих версиях прошли все 29 эталонных проверок и сохранился письменный разбор.
[Загрузчик оригинала](pseudocode/pg_course.c#L94) · [Загрузчик порта](../../src/app/server.mjs#L38)

## Что изменилось в рабочем порте

Сервер порта написан заново на Node.js. Следующие различия относятся к его
реализации и имеют значение при переносе работы или сравнении поведения.

| Область | Оригинал Windows | Рабочий порт |
| --- | --- | --- |
| Папки и резервные копии работ | Имя папки вычисляет `studentKey`. Оригинал сохраняет `workspace.json.bak` и читает его при ошибке разбора основного JSON. | Имя папки вычисляется по другой схеме. Ввод того же имени в порте открывает папку порта. `workspace.json` записывается атомарно, чтение резервной копии формата Windows отсутствует. |
| Настройки среды | `POST /api/compiler` сохраняет `compiler.json`. | Сервер возвращает конфигурацию встроенного PGlite. Ответ `200` на сохранение настроек не сопровождается записью файла. |
| Состояние приложения | `/health` отвечает статусом. При обычном запуске EXE может открыть уже работающий экземпляр через `instance.json`. | `/health` возвращает `404`. При запуске создаётся новый сервер. |
| Открытие папки | Оригинал открывает папку в Windows Explorer. | В Linux порт вызывает `xdg-open`. При запуске порта на Windows запрос возвращает путь, а каталог открывается вручную. |

## Повторение анализа

Нужны исходный Windows EXE, Python 3.9+, Go 1.27, JDK 25 и установленная
[Ghidra 12.2](https://github.com/NationalSecurityAgency/ghidra/releases/tag/Ghidra_12.2_build).
Архивы инструментов и проект Ghidra в репозиторий не включаются;
проверенные версии и SHA-256 загрузок записаны в `toolchain.json`.

Пример запуска из этой папки в Linux:

```bash
python3 tools/run_decompile.py   --input /path/to/PostgreSQL_JOIN90.exe   --ghidra /opt/ghidra_12.2_PUBLIC   --java /opt/jdk-25/bin/java   --go /usr/local/go/bin/go   --output ../../build/repeated-decompilation   --work-dir ../../build/ghidra-analysis
```

В Windows используйте `python` и соответствующие пути к `java.exe` и `go.exe`.
В `tools/` сохранены использованные скрипты импорта функций и экспорта
декомпиляции. Все служебные каталоги Ghidra направляются в `--work-dir`.
